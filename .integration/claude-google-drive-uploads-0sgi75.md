**Intent:** Let a reader add a document by picking it from Google Drive — a new upload method beside Upload PDF, Upload video, and Add URL.

**Files:**
- `src/lib/drive/types.ts` (new) — shared client+server classification: which mime types Drive can hand us, and what each becomes (`export` → PDF via Drive's own conversion, `pdf`/`media` → direct download, `unsupported` → declined). One definition so the picker's filter and the server's authoritative check can never drift apart.
- `src/lib/drive/config.ts` (new) — `driveConfig()`: server-side gate and the two values the client needs (`GOOGLE_CLIENT_ID`, optional `GOOGLE_PICKER_API_KEY`). Returns `null` (option hidden) when `GOOGLE_CLIENT_ID` is unset, the same DUAL MODE as `lib/auth.ts`'s sign-in providers.
- `src/lib/drive/picker-client.ts` (new) — the browser half: loads Google Identity Services + the Picker on demand, requests a `drive.file`-scoped OAuth token (cached in memory for the tab), opens the picker, resolves with the token and whatever was picked. Ambient `Window.google`/`Window.gapi` types are hand-declared (narrow, no `any`) since no `@types` package exists for these.
- `src/lib/drive/fetch.ts` (new, server-only) — downloads a picked file from Drive with the bearer token the client forwards: `fetchExportedPdf` (Docs/Sheets/Slides → `files.export?mimeType=application/pdf`) and `fetchDrivePdf` (`files.get?alt=media`, with the same size and `%PDF-` magic-byte checks a direct PDF upload gets). Maps Drive's error shapes to translated messages.
- `src/app/api/drive/import/route.ts` (new) — the route: validates the body, checks notebook edit access, extracts the bearer token, classifies the file, then branches to either `ingestMediaUrl` (video/audio) or `ingestPdf` (pdf/export) — the exact same ingest functions a local upload or a pasted URL already uses. Mirrors `/api/documents/route.ts`'s structure closely (dynamic `parse/ingest` import only on the branches that need it, same post-ingest glossary/connections/transcription side effects).
- `src/lib/video/ingest-media-url.ts` (edit) — `ingestMediaUrl` gained an `opts?: { headers?, title? }` param (was a lone trailing `headers?`). `headers` carries the bearer token for a Drive download; `title` was necessary, not cosmetic — the function's existing title fallback reads the last path segment of the URL, which for a Drive download URL is the file id, not a name, so without an override every Drive video/audio import would title itself after a long id string. The one existing caller (`/api/documents`) is unaffected.
- `src/components/reader/document-bar.tsx` (edit) — new `drive` prop, "Add from Google Drive" menu item (hidden when `drive` is null), and `importFromDrive()`: gets a token + picks files, then feeds each through the same `runIngest` progress-card path `uploadFiles` already uses, one at a time for multiple picks. Client-side pre-checks (unsupported type, over the 50 MB/200 MB caps) reuse `classifyDriveFile` so a bad pick fails before any network call.
- `src/components/reader/ingest-progress.tsx` (edit) — new `"drive"` progress-step template (fetch → parse → save) for the pdf/export branch; the video/audio branch reuses the existing `"media"` template unchanged (its steps already fit: fetch, save).
- `src/components/reader/workspace.tsx`, `src/app/n/[notebookId]/page.tsx` (edit) — thread `drive: DriveConfig | null` from the page (`driveConfig()`, computed server-side) down to `DocumentBar`. No new API route was needed for this — the two values aren't secret (a Google client id is a public identifier by design; the Picker key is scoped to the Picker API only), so passing them as RSC props avoids an extra round trip.
- `src/lib/i18n/dict/panes.ts`, `src/lib/i18n/dict/api.ts` (edit) — new en/zh strings: the menu item, the progress step, and the error messages (missing/expired token, unsupported type, Drive's own 10 MB export cap, a generic fetch failure), following the existing parallel phrasing of the sibling upload messages.
- `.env.example`, `.env.local.example` (edit) — documented `GOOGLE_PICKER_API_KEY` (optional) and the one extra Google Cloud console step this feature needs beyond sign-in (adding the app's origin to the OAuth client's "Authorized JavaScript origins" — a different list from the redirect URI sign-in uses).
- `SPEC.md` (edit) — new `## 14. Google Drive upload` section: the grant, the three-source ingest mapping, the dedupe difference between the video/audio path (sourceUrl) and the pdf/export path (content hash, same as any PDF), and the surface.

**Decisions:**
- **No persisted "connection."** The obvious alternative — a stored refresh token (a `GoogleDriveConnection` table, a Settings "Disconnect" control) — would need a DB migration, its own OAuth callback route, and long-lived credential storage for a third-party account. Instead the client gets a short-lived token straight from Google Identity Services each time and hands it to the import route for one immediate use; nothing Drive-related is ever written to the database. This also sidesteps the `userId` soft-reference wrinkle (`User` rows don't exist in single-local-reader mode) that a persisted-per-user connection would have run into.
- **`drive.file` scope + Picker, not `drive.readonly` + a custom file browser.** `drive.readonly` would show every file the picker offers today, without needing the separate Picker JS/API key — but Google classifies it as a *restricted* scope, requiring an annual security assessment to clear "unverified app" for a real public deploy. `drive.file` only grants access to what the reader explicitly picks in Google's own Picker UI, is a *non-sensitive* scope, and is what the same style of "Add from Drive" features generally use elsewhere. A different, reasonable call would take the simpler scope and accept the verification cost.
- **`GOOGLE_PICKER_API_KEY` optional, not required.** Google's docs list a developer key as expected for full Picker functionality (richer previews), but I could not verify from this sandbox whether the picker hard-fails without one. Gating the whole feature on a second credential most deployers won't think to create seemed like the wrong default, so the feature activates on `GOOGLE_CLIENT_ID` alone and the key is a documented, optional upgrade. Worth a real functional test against a live Google Cloud project — I could not exercise the OAuth/picker flow or the import route end to end in this sandbox (no `DATABASE_URL`, no Google credentials); verification here is `tsc --noEmit` and `eslint` clean, plus a careful reading of the ingest paths this route delegates to.
- **Scope of importable Drive content.** PDF, Google Docs/Sheets/Slides (exported to PDF), and video/audio — everything the existing ingest paths can already read. Raw `.docx`/`.xlsx`/`.pptx`, images, Forms, and Drawings are declined with a plain message rather than adding a fourth parser; SPEC.md's "one code path" rule for the derivation pipeline seemed worth extending to ingest as a matter of consistency, not just literal scope.
