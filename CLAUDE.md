# CLAUDE.md

## Text Production Style (applies to ALL text you write: UI copy, prompts, docs, comments, commit messages, and AI prompt templates in /lib/prompts/)

Do not use different phrases and sentence structures for the sake of using different phrases and sentence structures. The goal is to be simple, concise, and straight to the point — most easily interpretable and suitable for the target audience.

Concretely:

1. **Repetition of the right word beats variation.** If "note" is the correct term, write "note" every time. Never rotate through synonyms (annotation, entry, item, snippet) to avoid repeating a word. Synonym rotation forces the reader to check whether two words mean two things.
2. **One term per concept, everywhere.** The vocabulary is fixed: project (one binding of documents; the dashboard collection is Projects; code identifiers keep `notebook`/`corpus`), section, note, source, anchor, block, derivation, pending, accepted, extraction (one question and its quotes; code identifiers keep `distill`/`distillation`/`DISTILL`), quote, caption, match (one origin phrase and its revealing passages; the tool is Match-it; code identifiers keep `extract`/`extraction`/`EXTRACT`), digest (the stored project context the assistant reads: one row per project per user), share, collaborator (a person a project is shared with), role (owner / editor / viewer), person (the badge: name, symbol, color, picture), profile (the account's own settings page section), background (the one context field injected into prompts), thinking (how hard the assistant thinks about a message: Fast Thinking or Deep Thinking, one choice for every assistant surface), side chat (a conversation branched off a quote of an assistant answer; it belongs to the chat box it started in and never shows in assistant history), comment on an answer (a remark on quoted words of an assistant answer, listed under the thread; code keeps `Reply` rows on the conversation note), reply (one entry in the discussion under a note, an edit, or a link; resolve closes one), account (the signed-in identity), recommended link (an AI-proposed link awaiting Accept), graph (the project's documents and links drawn as nodes and curves), history (the project's record of edits and deletions), gist (the phrase a collapsed note or annotation shows in place of its first words when the note has no title; AI writes it to fit the row), title (a note's first line when it is a level-one heading; the row above the body, and the collapsed line), body (everything of a note after its title), merge (two notes made one: Join text puts the sources' text into the target as it is, the note on top first, and is what a hold and the ticker's Merge do; Merge with AI writes the one note that takes their place: the key points of each note, structured, each with the quotes that support it under it; a merge can be undone), hold (the gesture that picks a note up: the pointer stays on the card for a moment, the card lifts and tilts, and it follows the pointer; a note has a draggable mode and an editing mode, never both), hold ring (the ring a drag draws around the note it would merge into, once the dragged note covers it; at the full ring the merge runs), drop line (the line that says where a dragged card would land; cards hold still), link card (a link on a line of its own in a note, drawn as a row with the link's text and its site), board (one section's notes filling the screen as tiles side by side, opened from the notes full page by a click on the section's title; a tile shows its whole body when the board's rows have the room, and is a 3:4 tile, taller than wide, at the least; code keeps `SortableBoard` for the drag surface), tile (one note on a board), companion (one web app outside Unitos, listed under Projects on the dashboard, for a step around a document Unitos does not do; the section is Companions), visualization (the picture Visualize makes of a selection: a diagram, a picture, or an animation; the tool is Visualize; code identifiers keep `VISUALIZE`), tier (an account's plan: Unitos Premium or Unitos Ultra), trial (the two months of Unitos Premium a new account gets free), tier mark (the symbol beside a person's badge that says the tier: the white crystal is Unitos Premium, the black diamond is Unitos Ultra), tier chip (the mark and the tier's name in one pill), checklist (a list of task items, each with a box that ticks), dash list (a bulleted list drawn with a dash), notes full page (the page that shows every note of a project; never "full screen"), stitch (the assistant's command across the project's documents, run from the graph: gather passages, draw links, find contradictions, write a new page; the tool is Stitch; it reads the documents picked in the graph, or every document when none is picked), pick (a document selected in the graph for Stitch; a picked node draws a ring), generated document (a document Stitch wrote from the project's documents; `Document.generatedCommand` is the command that made it), skeleton (a document collapsed for Stitch: a gist, one summary per part, one line per block with every claim and number kept; `Document.skeleton`; rebuilt when more than a tenth of the document changed), route pass / select pass / answer pass (Stitch's three model passes: the parts, then the blocks, then the answer), contents (the article's parts, each a jump to where it starts; the button at the top left of the article; code identifiers keep `contents`), part (one entry of the contents: a title and the block it starts at), offline copy (a project's pages and images kept in the browser so the project opens without a network; the action is Save for offline, the badge is Offline, the page that lists the saved projects offline is the offline page; Unitos Ultra), voice command (a command spoken in a section of the notes tray: the assistant reads the open document and the section's notes and writes the notes the command asks for, each quote a source, as pending notes; the button is Command; code identifiers keep `voice`/`VOICE`), annotation reference (a line in a note that points to an annotation: an annotation dragged onto a note lands as one; a click opens the annotation, beside the note on the notes full page, else in the reader; `lib/annotation-reference.ts`), vision check (the last pass of a URL import: the page and the reader's rendering of the blocks pictured in a browser and compared by the vision model, which answers with ops by block index; `lib/parse/vision-check.ts`). Use these exact words in UI, code, prompts, and docs. Never introduce a second name for an existing concept. The same rule holds in Chinese: the zh glossary at the top of `src/lib/i18n/dict/common.ts` fixes one Chinese term per concept — every namespace keeps to it.
3. **Default to the same sentence structure for parallel content.** Error messages, empty states, tooltips, and prompt instructions that do parallel jobs should have parallel structure. Uniformity is a feature, not a flaw.
4. **Cut preamble and postamble.** No "Let's dive in", no "In summary", no restating what was just said. Start with the point.
5. **Short sentences. Concrete words.** Prefer "Click a source chip to jump to the highlight" over "Selecting the associated source indicator will navigate the user to the corresponding highlighted region."
6. **Casual is fine; vague is not.** Plain conversational language is acceptable when it carries a precise, logical point. Never trade precision for polish.
7. **Prompt templates follow the same rules.** Instructions to the model should be blunt, ordered, and unadorned. No elegant variation inside prompts — repeated exact terms improve model compliance.

## Project Conventions

- Read SPEC.md before writing any code. It is the source of truth for data model, phases, and quality bars.
- Build in the exact phase order in SPEC.md §8. Do not start a phase before the previous phase's "Done when" criteria pass.
- The derivation pipeline (SPEC.md §4) is one code path. Never fork it per feature. New features = new prompt template + destination handler only.
- Anchors: dual strategy per SPEC.md §5. DOM ranges are never persisted.
- All AI output destined for notes is `status: PENDING` until user accepts. No exceptions.
- TypeScript strict mode. No `any`. Zod-validate every API request body and every LLM JSON output.
- Prompt templates live in `/lib/prompts/`, one file per DerivationType, each exporting a single function `(ctx) => string`.
- Keep components small; server components by default, client components only where interaction requires it.
- After each phase, run the app and verify the "Done when" criteria manually before moving on. State plainly which criteria pass and which do not.
- Deploys: Vercel builds `main`. After the user accepts a change, push it to `main` — the user has standing instructions to auto-deploy accepted work.

## Parallel round rules

### Worker sessions
- Work only in your own worktree. Never checkout, merge, or push another branch.
- Never touch `main` or `integration`.
- Commit after each logical unit of work.
- Before finishing, write and commit `.integration/<your-branch-slug>.md` containing:
  - **Intent:** one sentence on what you were asked to do
  - **Files:** each path you changed, and why
  - **Decisions:** any choice a reasonable person could have made differently
- Then stop. Do not merge.

### Orchestrator session (branch `integration`)
- Only consider branches that have commits not on `origin/main` AND have a file under `.integration/`. Ignore everything else regardless of name.
- Never write application code except to resolve a conflict.
- Report findings first. Wait for explicit approval before merging or editing anything.
- Merge branches one at a time. Run tests after each merge. Once a branch's tests pass, delete that branch immediately — local and remote — before merging the next one.
- Never send a conflict back to the worker that wrote the code.
- After the last branch's tests pass, finish the round without waiting for further approval: delete the round's intent files under `.integration/` (keep `.gitkeep`), commit, merge `integration` into `main`, push `main`, then delete `integration` — local and remote.
